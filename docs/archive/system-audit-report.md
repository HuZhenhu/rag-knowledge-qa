# RAG 系统全量体检报告

> 日期：2026-07-16
> 方式：实际启动系统，通过 API 发送 7 类测试问题 + 8 环节功能检查
> 结论：发现并修复 8 个问题，全部环节复测通过

---

## 一、体检方法

启动系统后，通过 `/api/v1/query` 等接口发送以下测试：

| 类别 | 示例问题 | 目的 |
|------|---------|------|
| 正常单文档 | 什么是RAG？ | 验证基础问答 |
| 正常跨文档 | 做一个AI应用工程师需要掌握哪些技能？ | 验证多文档综合 |
| 部分无关 | RAG的原理是什么？顺便讲讲量子力学 | 验证无关部分拒绝 |
| 完全无关 | 量子力学和黑洞的关系 | 验证相关性过滤 |
| 模糊 | 这些东西有什么用？ | 验证模糊处理 |
| 诱导编造 | LangChain和相对论有什么关系？ | 验证防幻觉 |
| 超长/空 | 哈*500 / 空字符串 | 验证健壮性 |

检查 8 个环节：检索质量、查询理解、引用可追溯、接口健壮性、鉴权、多轮对话、文档管理、评测接口。

## 二、发现的问题及修复

### 问题1：主接口崩溃（高严重度）
**现象**：所有 `/api/v1/query` 请求返回 500
**根因**：`routes.py` 访问 `response.intent` 属性，但 LangChain 引擎返回对象无此属性
**修复**：改用 `getattr(response, "intent", "")` 兜底

### 问题2：DeepSeek API Key 失效（高严重度）
**现象**：所有 LLM 调用返回 401 authentication error
**根因**：系统环境变量 `OPENAI_API_KEY`（旧key）覆盖了 `.env` 里的新 key
**修复**：临时用环境变量传入有效 key；建议在系统环境变量中删除旧 key

### 问题3：检索数量失控（高严重度）
**现象**：`top_k` 传 5，实际返回 17-26 条
**根因**：LangChain 引擎的 `query()` 没把 `top_k` 传给检索器
**修复**：改用 `vectorstore.similarity_search_with_score` + 手动截断

### 问题4：来源文件名显示"未知"（高严重度）
**现象**：所有引用来源文件名都是"未知"
**根因**：metadata 字段是 `source_file`，代码读的是 `source`
**修复**：两处都改为 `source_file` 优先，`source` 兜底

### 问题5：检索无相关性过滤（高严重度）
**现象**：完全无关的问题（量子力学、养花）也返回 5 条来源
**根因**：score 是硬编码排名分 `1.0 - i*0.1`，无真实相似度
**修复**：
- 改用 `similarity_search_with_score` 拿真实相似度
- 设置 `RELEVANCE_THRESHOLD=0.45` 过滤低相关结果
- 效果：无关问题来源数从 5 条降到 0 条

### 问题6：图片文件误排检索结果首位（中严重度）
**现象**："什么是RAG" 首条来源是 `test_ocr.png`
**根因**：图片 OCR 描述和文本 chunk 混排，score 只看排名
**修复**：真实 score 生效后，图片不再虚高排名

### 问题7：admin 用户无管理权限（高严重度）
**现象**：`GET /api/v1/evaluations` 返回 403
**根因**：数据库里 admin 用户角色是 viewer
**修复**：授权后升级为 admin 角色

### 问题8：文档列表"只返回2个"（误报）
**现象**：体检脚本显示 2 个文档，实际知识库 45 个
**根因**：体检脚本 `len()` 数的是顶层 key 数（documents + total），不是文档数
**修复**：修正体检脚本，实际返回 39 个文档

## 四、遗留优化项

1. **阈值过滤不完全**：对"边缘相关"问题（如"用Go写微服务"），score 0.52 能过 0.45 阈值，但 LLM 已能正确拒绝。可后续用动态阈值或 LLM 相关性判断改进。
2. **检索执行两次**：`query()` 单独检索一次取 sources，chain 内部又检索一次生成 context。结果一致但浪费一次检索时间。
3. **Embedding 中文区分度**：bge-m3 对中文问题"相关"和"无关"的分数差距小（0.44~0.58），可考虑切换更好的中文 embedding。

## 五、评测体系与调优记录

### 5.1 评测体系建设

| 阶段 | 内容 |
|------|------|
| 基线评测 | 修复评测脚本引擎不一致 + 两个bug，30条评测集跑通 |
| 四维评测 | 实现 LLM-as-Judge 四维指标（相关度/忠实度/帮助度/正确度） |
| 评测集扩充 | 从知识库3751个chunks生成61条，合并成91条，覆盖7领域 |
| 段错误修复 | 引擎与embedder重复加载同一模型导致段错误，改为复用 |

### 5.2 控制变量调优结果

**参数1：top_k（91条关键词模式）**

| top_k | 准确率 | 检索命中率 | 引用率 |
|-------|--------|-----------|--------|
| 3 | 70.5% | 76.9% | 97.8% |
| 5 | 76.8% | 85.7% | 94.5% |
| **7** | **78.7%** | **87.9%** | 92.3% |

**结论**：top_k=7 最优。检索越多相关文档，回答越完整。已将 `RETRIEVAL_TOP_K` 从默认10改为7。

**发现隐藏bug**：`.env` 里的 `TOP_K=5` 从未生效——config 读的是 `RETRIEVAL_TOP_K`（默认10）。修正为 `RETRIEVAL_TOP_K=7`。

**参数2：relevance_threshold**

| 阈值 | 准确率 | 检索命中率 | 引用率 |
|------|--------|-----------|--------|
| 0.35 | 74.8% | 85.7% | 95.6% |
| **0.45** | **77.0%** | 85.7% | 95.6% |
| 0.55 | 74.7% | 82.4% | 93.4% |

**结论**：relevance_threshold=0.45 最优（当前配置已正确）。0.35 引入噪声，0.55 过滤过严。

### 最终参数组合
- `RETRIEVAL_TOP_K=7`
- `RELEVANCE_THRESHOLD=0.45`

**调优方法论**：用91条评测集 + 关键词模式（每轮5分钟）做控制变量实验，找最优参数后用四维模式验证。
