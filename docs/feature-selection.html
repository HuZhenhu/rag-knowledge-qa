RAG系统功能选型分析

跨文档查询合并 & 增量更新策略

一、跨文档查询合并方案

场景：用户问"张三的基本信息和爱好是什么？"
信息分散在多个文档中，需要综合多个来源回答
方案 原理 延迟 成本 效果 复杂度
推荐 多子查询拆分 LLM拆成多个子查询，分别检索后合并 低 低 好 低
推荐 HyDE LLM生成假设回答，用假答案去检索 中 中 很好 低
备选 查询重写 LLM改写用户问题为更适合检索的形式 低 低 中 低
备选 多跳检索 迭代式检索，每次结果作为下次上下文 高 高 很好 高
复杂 GraphRAG 构建知识图谱，用图查询补充向量检索 高 很高 很好 很高

推荐方案：多子查询拆分 + HyDE + 混合检索 + ReRanker

  • 多子查询拆分：覆盖问题的多个维度
  • HyDE：跨越"语义鸿沟"，提高检索命中率
  • 混合检索（向量+BM25）：语义+关键词双保险
  • ReRanker：精排，过滤噪声
  • 增强prompt：明确告诉LLM要综合多个来源

为什么推荐这套方案

  • 实现简单，你已经有了大部分模块
  • 延迟低，用户体验好
  • 成本低，只多几次LLM调用
  • 效果好，覆盖90%以上的场景

为什么不推荐GraphRAG

  • 你的文档是技术知识，不是人物关系图
  • 构建成本高，24个文档要花不少时间
  • 维护成本高，每次新增/修改文档都要更新图谱
  • 延迟高，用户体验差
  • 过度设计，杀鸡用牛刀

实现方式：增强prompt

# 在 generator.py 的 prompt 中加入 你是知识库问答助手。请综合以下多个来源的信息回答。 规则： 1. 如果信息来自多个来源，综合整理，不要遗漏 2. 如果不同来源有矛盾，都列出并说明来源 3. 每个论断标注来源 参考资料： [来源1] 03-RAG检索增强生成.md（什么是RAG）：RAG的全称是... [来源2] 04-LangChain基础.md（检索链路）：LangChain支持... [来源3] 05-Dify平台.md（Dify是一个开源平台...

整体架构

用户提问 | [1] 查询扩展：LLM拆成3-5个子查询 | [2] HyDE：生成假设回答（可选） | [3] 混合检索：向量检索 + BM25检索 | [4] RRF融合：合并两路结果 | [5] ReRanker：精排过滤噪声 | [6] LLM生成：综合多个来源，标注引用 | 返回结果：回答 + 引用来源

二、增量更新策略方案

场景：修改文档的一小部分，只更新受影响的chunks，不重建整个索引
方案 原理 更新成本 一致性 复杂度
备选 全量重建 每次修改重新处理整个文档 高 完美 低
推荐 文档级Replace 删除文档所有旧chunks，重新切片+embedding 中 完美 低
推荐 Chunk级Content Hash 对比每个chunk的hash，只更新变化的 低 好 中
复杂 CDC算法 用Gearhash让chunk边界由内容决定 很低 好 很高
复杂 版本化Chunk ID 用doc_id + content_hash作为ID 低 好 高

推荐方案：Chunk级Content Hash（分阶段实施）

  • Phase 1：Content Hash对比，跳过未变化的chunks
  • Phase 2：Chunk级Upsert，按ID替换变化的chunks
  • Phase 3（可选）：CDC算法，精确控制边界稳定性

为什么推荐Content Hash

  • 实现简单，只需要计算SHA-256
  • 效果好，50倍成本差距（50万文档2%变更率）
  • ChromaDB原生支持upsert
  • 分阶段实施，风险可控

为什么不推荐CDC

  • 实现复杂，需要引入新算法
  • 你的场景不需要精确的边界稳定性
  • Content Hash已经够用
  • 过早优化，增加维护成本

实现方式：Content Hash对比

import hashlib def compute_chunk_hash(content: str) -> str: """计算chunk的内容hash""" return hashlib.sha256(content.encode()).hexdigest() def incremental_update(doc_path: str, old_chunks: list): """增量更新""" # 1. 重新切片（新chunks） new_chunks = split_document(doc_path) # 2. 对比hash，找出变化的chunks old_hashes = {compute_chunk_hash(c.content): c for c in old_chunks} to_update = [] to_delete = set(old_hashes.keys()) for chunk in new_chunks: chunk_hash = compute_chunk_hash(chunk.content) if chunk_hash in old_hashes: # 未变化，跳过 to_delete.discard(chunk_hash) else: # 变化了，需要更新 to_update.append(chunk) # 3. 删除旧的，插入新的 vectorstore.delete(where={"source_file": doc_path}) if to_update: vectorstore.add(to_update)

整体架构

文档修改 | [1] 重新切片（新chunks） | [2] 计算每个chunk的content_hash | [3] 对比旧chunks的hash | [4] 找出变化的chunks | [5] 只embedding变化的chunks | [6] Upsert到向量库（按ID替换） | 完成：增量更新，成本降低50倍

三、总结

最终推荐方案

  • 跨文档查询：多子查询拆分 + HyDE + 混合检索 + ReRanker + 增强prompt
  • 增量更新：Content Hash对比 + Chunk级Upsert
  • 核心原则：简单够用，不过度设计

重要提醒

知识图谱（GraphRAG）适合实体关系密集的场景（人物关系、组织架构），不适合技术文档问答场景。不要被最近的热度迷惑，选择适合自己的方案才是最好的。
