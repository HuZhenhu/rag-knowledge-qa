## 【设计点1】混合检索 + RRF 融合（向量 + BM25 双通道）

### 1. 问题
单路向量检索有两个盲区：① 专有名词/编号/短查询（如"治安管理处罚法第几条"）语义向量召回差；② 高频实体在 embedding 空间被"平均化"，精确词匹配失效。需要一条"字面命中"通道兜底。同时两路分数量纲不同（cosine 距离 vs BM25 词频分），不能直接相加，需要一个不依赖分数绝对值的融合排序算法。

### 2. 选型
- 关键词通道选 **BM25（Okapi BM25）** 而不是 TF-IDF / Elasticsearch：BM25 带词频饱和（k1、b 参数）和文档长度归一，对长文档更稳；rank_bm25 是纯 Python 零依赖，可直接在进程内对全量 chunk 建索引，不需要额外起 ES 服务。
- 中文分词选 **jieba**：默认 BM25 按空格切词对中文无效，必须分词器；jieba 是事实标准、支持自定义词典。
- 融合选 **RRF（Reciprocal Rank Fusion）** 而不是分数加权平均 / 归一化后相加：两路分数分布完全不同，归一化会引入偏差；RRF 只看排名，`1/(k+rank)` 天然无量纲、鲁棒，k=60 是业界常用经验值（源自 Cormack et al. 2009）。
- 项目还做了**加权扩展**：`w_v/(k+rank_v) + w_b/(k+rank_b)`，两路权重可配（config 里默认 1.0/1.0，LangChain 版用 0.6/0.4），这样某一通道的可信度可以调。

### 3. 实现（真实代码）
- 双通道入口：`src/core/retriever.py` 的 `HybridRetriever.retrieve()`（L69-78）：
  ```
  向量检索  self._vector_search(query, top_k)     # L80-97
  BM25检索  self._bm25_search(query, top_k)       # L99-119
  RRF融合  self._rrf_fusion(vector_results, bm25_results, top_k)
  ```
  ⚠️ 诚实说明："并行"是**逻辑并行（两条通道各拿一份 top_k）**，物理上代码是顺序调用，没有开线程；项目里真正的线程并行只出现在跨知识库检索 `vector_store.py` 的 `query_multi_kb`（ThreadPoolExecutor，L343）。
- BM25 索引构建：`retriever.py` L60-67，`build_bm25_index` 用 `[list(jieba.cut(doc)) for doc in documents]` 全量分词建 `BM25Okapi`；查询侧 L104-105 同样 `jieba.cut` 后 `get_scores`，`argsort()[-top_k:][::-1]` 取 top。
- 索引数据来源：`src/core/rag_engine.py` `_build_bm25_index()`（L109-123）在引擎初始化时 `vector_store.get_all()` 拉全量文档灌进 BM25。**索引构建失败降级**就在这个 try/except 里：L121-123 `logger.warning(...)` 后直接 `self.retriever = Retriever(...)`，即**运行时切换为纯向量检索器**，服务不炸。
- RRF 实现：`retriever.py` L121-171。要点：
  - 合并用 `all_docs` 字典，**key 是 `content[:100]` 前100字符**（L134）；
  - 某路没召回的文档，另一路排名补 `len(results)+1`（L139、L149），保证只有一路命中也有分；
  - 分数 `w_v/(k+rank_v) + w_b/(k+rank_b)`，k 来自 `config.RRF_K`（默认 60），权重来自 `HYBRID_VECTOR_WEIGHT`/`HYBRID_BM25_WEIGHT`（默认 1.0/1.0）；
  - 排序后 `[:top_k]` 截断。
- 参数：`src/config.py` L46-48：`RETRIEVAL_TOP_K=10`（.env 里覆盖为 5）、`RRF_K=60`、`USE_HYBRID_RETRIEVAL=true`。
- LangChain 版（`src/core/langchain_rag.py`）：`_setup_hybrid_retriever()`（L103-125）用 `BM25Retriever.from_texts` + `EnsembleRetriever(retrievers=[vector, bm25], weights=[0.6, 0.4])`（L115-118），初始化失败同样 `use_hybrid=False` 回退纯向量（L123-125）。

### 4. 追问预案
- Q：RRF 为什么用排名不用分数？→ 两路分数量纲/分布不同（cosine 距离 0~2，BM25 可到几十），直接加会偏向某一通道；RRF 只看相对次序，天然鲁棒，这也是为什么 RRF 是"无监督融合"的默认选择。
- Q：k=60 怎么来的？→ 经典论文的经验值，k 越大越"平滑"（对排名差异不敏感）；可以在小评测集上扫参，我们没扫，直接用 60。
- Q：BM25 索引什么时候建？数据变了怎么办？→ 引擎初始化时从 Chroma 全量拉取构建，内存里是静态的；新文档上传后需要重建（LangChain 版 `add_documents` 末尾会调 `_setup_hybrid_retriever` 重建，L389-392；原版引擎靠重启或增量索引后重建）。
- Q：两路都命中的文档怎么去重？→ RRF 里按 content[:100] 合并；后续多子查询合并还有一层 md5 全内容去重（见设计点2）。
- Q：为什么还留了权重参数？→ 实测中如果发现精确词匹配更重要（比如编号类查询多），可以调高 BM25 权重，不用改代码，config 驱动。

### 5. 边界（实话实说）
- **RRF 去重 key 用 content[:100]**：两个不同 chunk 前 100 字符相同会被误判为同一文档而丢失；反过来同一文档如果内容被改过前 100 字符，又会变"两份"。这是一个已知简化。
- **BM25 索引是启动时全量构建**：3751 个 chunk 全量 jieba 分词 + 建索引有秒级开销，且**不在向量库更新时自动同步**（原版引擎需重启/重建）。
- **物理上不是并行**：两路检索顺序执行，latency 是相加不是取 max；要真并行得用 ThreadPoolExecutor 包一层。
- **纯内存索引**：BM25 索引不持久化，进程重启重建。
- LangChain 版有个隐藏坑：**`query()` 主路径（非流式）实际没用 EnsembleRetriever**——它直接 `vectorstore.similarity_search_with_score`（L208），只有 `query_stream` 走 `retriever.invoke`（L316-317）。也就是说默认引擎的主接口里"混合检索"是打了折扣的，只有流式接口是真混合。

## 【设计点2】查询理解三阶段：纠错 / 扩展 / HyDE

### 1. 问题
用户 query 通常是口语化、有错别字、单一句子，直接拿去检索会：① 错别字导致向量和 BM25 双双 miss；② 复杂问题只检索一次覆盖不全（召回低）；③ query 与文档存在"问法鸿沟"——用户问"怎么部署"，文档写"安装步骤"。三个问题分别对应三阶段处理。

### 2. 选型
- 全部用 **LLM 做**而不是规则/词典：中文错别字（同音字）和子查询拆分都需要语义理解，规则表维护成本高且覆盖差；DeepSeek API 便宜，单次调用几十 token。
- **纠错放最前**：错别字会污染后面所有阶段（扩展、HyDE、检索），所以先修。
- **扩展选"多子查询"而不是"改写单句"**：多路召回直接提召回率，且每个子查询可独立走混合检索。
- **HyDE（假设性文档）**：让 LLM 先写一段"知识库里会有的回答"，用这段文字去检索——因为 query 和文档的表述风格差异大，而"假设回答"的表述风格更接近文档，embedding 更近（Gao et al. 2022）。本项目把它做成**可选通道**而非默认，因为多一次 LLM 调用 + 一次检索，延迟和成本都增加。
- 开关全部走 config/构造参数：实验驱动，控制变量（这也是设计点4评测调优的前提）。

### 3. 实现（真实代码）
文件：`src/core/query_understander.py`；编排：`src/core/rag_engine.py` L195-237（非流式 query 主链路）。
- **纠错** `correct_query()`（L98-132）：prompt 要求"只修正明显错别字和同音字（如'心法'→'新法'），没有就原样返回"；`temperature=0.1`、`max_tokens=200`；失败或返回空则原样返回。开关：`USE_QUERY_CORRECTION`（config 默认 **true**，.env 未覆盖）。
- **扩展** `expand_query()`（L42-96）：prompt 要求拆 **3-5 个不同角度子查询**，返回 JSON `{expanded_queries, entities, intent}`；用正则 `re.search(r'\{.*\}', text, DOTALL)` 抽 JSON（L75），解析失败/LLM 失败都**降级为 `[原查询]`**（L91-96）。开关：`use_query_expansion` 构造参数，config `USE_QUERY_EXPANSION` 默认 **false**（评测指南明确"暂不启用"，怕引噪声）。
- **HyDE** `generate_hyde()`（L134-161）：prompt 要求生成 100-200 字"像文档内容"的假设回答；`temperature=LLM_TEMPERATURE(0.7)`、`max_tokens=300`。rag_engine L215-230：对 hyde 文本 `embed_single` → `vector_store.query` 检索，结果**固定 score=0.5** 混入候选池（L229），随后统一排序。开关：`use_hyde` 构造参数，config `USE_HYDE` 默认 **false**（.env 显式 `USE_HYDE=false`）。
- **合并与去重**：rag_engine L244-259，`for q in expanded_queries: self.retriever.retrieve(q, top_k)` 多路结果 `extend`，再 `hashlib.md5(result.content).hexdigest()` 全内容去重（L251-259）——这就是"hash 去重"的真实位置。
- 各阶段耗时都进 `timing["query_understanding_ms"]` 并写入 trace span（L195-237）。

### 4. 追问预案
- Q：扩展子查询会不会放大噪声？→ 会，这是评测第2轮放弃默认开启的原因：多路召回带回 test_ocr.png 等无关 chunk，精准度下降（见 docs/ragas-optimization-guide.md 第2轮）。所以设计成开关 + 后续用 Reranker 精排兜底。
- Q：纠错为什么不用 pypinyin/规则？→ 同音字纠错依赖上下文（"新发" vs "心法"），规则表无法穷举，LLM 成本低且我们已有 DeepSeek 通道，复用即可。
- Q：HyDE 的 score=0.5 会不会污染排序？→ 0.5 只是给 hyde 结果一个"中等置信"的初始值，后面 Reranker 会重新打分；如果没有 reranker，0.5 也可能被截断在 top5 之外，属于可接受简化。
- Q：三个阶段的调用顺序为什么是纠错→扩展→HyDE？→ 纠错产生干净 query；扩展基于干净 query；HyDE 也基于干净 query。任何一步失败都降级为"原 query 继续"，保证链路不断。
- Q：多子查询各自 top_k 再合并，会不会把某个子查询的结果挤掉？→ 会，合并后按 RRF 分排序取 top_k，冷门子查询的结果可能出局，这是有意的（让强相关结果胜出）。

### 5. 边界
- **扩展/HyDE 默认关闭**：当前线上默认只有纠错开着，简历上不要讲成"默认全开"。
- 每阶段都多一次 LLM 调用：纠错+扩展+HyDE 全开会加 3 次串行 LLM 往返，延迟明显（基线 30 条评测平均 3.4s，部分就是 LLM 调用开销）。
- JSON 解析靠正则 `\{.*\}`：LLM 输出里若有多段 JSON 或花括号嵌套，可能抽错；只 try 一次，失败静默降级，不重试。
- `expand_query` 的 entities/intent 字段**下游基本没消费**（只回传展示），属于"能力预留"。

## 【设计点3】意图识别（关键词+LLM 分层）+ 查询 LRU 缓存

### 1. 问题
① 不是所有输入都该走 RAG：闲聊、反馈、追问应该分流，否则浪费检索+LLM 成本，且体验差；② 高频相同问题（同一个 query + top_k）每次都重跑 embedding 检索 + BM25 + rerank，纯浪费。

### 2. 选型
- 意图识别用 **"关键词快判 → LLM 兜底"两级**：关键词是 O(1) 命中、零成本、可解释；LLM 用 `temperature=0.0`、`max_tokens=20` 把输出压到最小。这是典型的"便宜的先判，贵的兜底"分层策略，避免每个请求都花一次 LLM 调用。
- 四类意图 `query/followup/chitchat/feedback`（`intent_classifier.py` L14-19 枚举）覆盖了 RAG 系统的典型分流场景：query 走全链路；chitchat 直接 LLM；feedback 记录；followup 由检索分低触发。
- 缓存选 **cachetools.TTLCache**（1000 条 / 1h TTL）而不是自己写 dict：TTLCache 底层就是 LRU + 过期淘汰，库成熟、线程安全（有锁）。**只缓存检索结果（sources），不缓存回答**——因为回答依赖 history/summary（多轮上下文），缓存回答会串味。
- key 用 `md5("{query}|||{top_k}")`：query+top_k 决定了检索行为，key 稳定、定长。

### 3. 实现（真实代码）
- **意图识别**：`src/core/intent_classifier.py`
  - 关键词表：`_KEYWORDS_FEEDBACK`（"不对/错误/不准确/没用..."，L36-39）、`_KEYWORDS_CHITCHAT`（"你好/你是谁/谢谢/再见..."，L32-35）。
  - `classify()`（L47-72）：先查 feedback 关键词（**不要求无历史**，L63-64）；chitchat 关键词**仅在第一轮（无历史）生效**（L67-69，防止多轮对话里"谢谢"被误判成闲聊而丢掉上下文）；都 miss 才调 LLM（L72）。
  - `_classify_with_llm()`（L74-108）：prompt 列出四类定义，`temperature=0.0, max_tokens=20`；输出里包含哪个枚举值就命中哪个（L99-101）；LLM 失败/解析失败默认 **query**（L104、L108）——**fail-safe 往 RAG 走**，不吞问题。
- **路由**：`src/core/rag_engine.py`
  - `classify_intent()`（L97-107）：`USE_INTENT_CLASSIFICATION` 默认 false，关了直接返回 "query"。
  - chitchat → `generator.generate(question, sources=[])` 直接 LLM，sources 空（L146-158）。
  - feedback → 直接返回固定感谢语，零检索零 LLM（L160-169）。
  - **主动追问 followup**（L303-318）：检索后 `pre_filter_count == 0` 且 `max_score < FOLLOWUP_SCORE_THRESHOLD(0.3)` 且 `has_history` 时，`_generate_followup()`（L74-95）让 LLM 生成引导追问语句，标记 `is_followup=True`。
- **LRU 缓存**：`src/core/query_cache.py` 全文 42 行
  - `TTLCache(maxsize=1000, ttl=3600)`（L17）；`_make_key` = `md5(f"{query}|||{top_k}")`（L20-23）。
  - 命中路径：rag_engine L172-188，`cached = self.query_cache.get(...)`，命中则按 `RELEVANCE_THRESHOLD` 过滤后**仍要调 generator 生成回答**（L176-178），sources 直接复用缓存的；未命中走全链路，**末尾 `self.query_cache.set(question, top_k, sources)` 写缓存**（L354）。
  - `clear()`/`size` 属性提供管理接口（L35-42）。

### 4. 追问预案
- Q：为什么缓存不缓存最终答案？→ ① 回答依赖 history 和 summary，同一 query 在不同会话/轮次答案应不同；② 缓存回答等于缓存"旧知识"，知识库更新后必须失效，而缓存检索结果只要知识库变了整体清空即可（cachetools 的 clear）。
- Q：TTLCache 和 LRU 什么关系？→ TTLCache 同时具备容量上限（超了按 LRU 淘汰最久未用）和 TTL 过期（超时惰性删除）两个维度，正好满足"1000 条 + 1 小时"。
- Q：为什么 feedback 关键词不要求无历史，chitchat 要？→ "不对/说错了"在任何轮次都是明确反馈信号；而"谢谢/好的"在对话中常是礼貌接话，若判成 chitchat 会截断多轮上下文，所以只在一开始生效。
- Q：缓存 key 为什么带 top_k？→ 检索行为由 query 和返回条数共同决定，不同 top_k 的结果集不同，混用会拿到错误条数的 sources。
- Q：意图识别误判了怎么办？→ 最坏情况是 chitchat 误判成 query（多花一次 RAG 成本）或 query 误判成 chitchat（返回无来源回答）；所以 LLM 侧默认值设为 query，宁可多检索也不错答。
- Q：缓存命中时 latency 是多少？→ timing 里 `"cached": True`，检索+rerank 全跳过，只剩一次 LLM 生成。

### 5. 边界
- `USE_INTENT_CLASSIFICATION` 和 `USE_CONVERSATION_SUMMARY` 默认都是 **false**，需要 .env 显式开。
- 缓存是**进程内内存**：多实例部署各自一份、不共享；进程重启全丢（cachetools 无持久化）。
- 缓存 TTL 是"创建后 1 小时"，不是"命中后顺延 1 小时"——热数据 1 小时后照样过期重建（cachetools TTLCache 的默认语义）。
- followup 检测依赖 `FOLLOWUP_SCORE_THRESHOLD=0.3` 和 has_history，且只在 `pre_filter_count == 0` 分支里触发——如果检索有结果但分低，不会触发追问。
- 关键词表很短（各 8-9 条），覆盖不全，多数情况其实落到了 LLM 分类。

## 【设计点4】RAGAS 评测体系（评测集自动生成 + 四维指标 + 控制变量调优）

### 1. 问题
RAG 系统"感觉好了"不算数，需要：① 一套可复现的评测集；② 覆盖"检索"和"生成"两个环节的多维指标（单看准确率定位不了瓶颈）；③ 每次改参数有客观对比，避免拍脑袋调优。

### 2. 选型
- 评测集**从 chunks 自动生成**而不是手写：知识库 3751 个 chunk 手写不现实，用 LLM 对每个抽样 chunk 生成"该 chunk 能回答的问题 + 标准答案 + 关键词 + 来源文件"，保证 ground truth 可溯源（答案一定在知识库里）。
- 指标框架选 **RAGAS**（arXiv:2309.15217）：它把评测分成检索侧（上下文精准度/召回率）和生成侧（忠实度/答案相关性），配合 2×2 诊断矩阵能定位"是检索漏了还是生成编了"——这正是本项目 docs/ragas-optimization-guide.md 的核心用法。
- 判分用 **LLM-as-Judge** 而不是字符串匹配：忠实度要判断"论断能否被上下文支持"，这是开放语义判断，规则做不了。
- 辅助的**关键词/引用/语义相似度**指标保留：便宜、快、可解释，适合全量 232 条跑批；四维 LLM 判分贵，适合子集精评。

### 3. 实现（真实代码）
- **评测集生成**：`scripts/generate_eval_data.py`
  - 从 `engine.vectorstore.get()` 拉全部 chunks（当前 Chroma `knowledge_base` 集合实测 **3751 条**，已核对 chroma.sqlite3）；
  - 过滤图片/OCR chunk、`len(text) < 50` 的碎片（L152-165）；
  - **分层抽样**：按源文件分组，每文档 `random.sample` 最多 3 个（L175-184，seed=42 可复现）；
  - 对每个 chunk 用 LLM 生成 `{question, expected_answer, expected_keywords}`（L73-136），过滤"泛泛问法"（`VAGUE_PATTERNS`，L45-49），按问题前 20 字去重（L211-215）；
  - 产出 `evaluation/test_cases_250.json`，实测 **232 条**：simple_fact 216 / multi_doc 9 / vague 4 / out_of_scope 3。→ 这就是"3751 chunks → 232 条"的完整链路。
- **四维指标**：`src/core/eval_metrics.py`
  - `evaluate_faithfulness`（L80-116）：回答拆成原子论断（LLM）→ 每条论断用 LLM 判"支持/不支持"→ `supported/claims`（最多验 10 条控成本）。
  - `evaluate_answer_relevancy`（L123-165）：LLM 从回答反推 3 个问题 → 与原问题做 embedding 余弦相似度取均值（这就是 RAGAS 的官方做法）。
  - `evaluate_context_precision`（L172-198）：每个检索 chunk 让 LLM 判"相关/不相关"→ `相关数/总数`（测噪声）。
  - `evaluate_context_recall`（L205-242）：标准答案拆论断 → 逐条判断检索上下文能否支持 → `被支持数/总数`（测遗漏）。
  - 总分 = 四维等权 0.25 加权（L270-275）。分数提取 `_extract_score`（L50-63）对 1-5 分制自动归一化。
- **跑批与汇总**：`evaluate.py`
  - `run_single_test`（L112-214）：单条 = 关键词分（`keyword*0.5 + length*0.2 + citation*0.3`，L56）+ 语义相似度（bge-m3 算余弦，L68-77）+ 检索命中率（来源文件归一化匹配，L80-99）+ 引用正确率（正则 `[来源\d+]`，L102-105）；`out_of_scope` 类目看是否"承认不知道"（L155-164）。
  - `compute_summary`（L303-358）产出五个核心字段：`retrieval_hit_rate / answer_accuracy / citation_accuracy / avg_semantic_similarity / avg_latency_ms` + `category_accuracy` + `avg_dimensions`。
  - 结果落 `evaluation/eval_{version}.json`，报告落 `report_{version}.md`，支持 `compare_evaluations` 版本对比（L482+）。

- **控制变量调优过程**（docs/ragas-optimization-guide.md 第1-4轮）：

  - 第3轮：`temperature 0.1→0.0` → 总分仅 +0.005，结论"瓶颈在检索不在生成"。
  - 第4轮：Reranker 精排（bge-reranker-base，下载 1.1GB 权重）。
  - 方法论：**每次只改一个变量，14 条子集快速验证，达标再全量**。

### 4. 追问预案
- Q：为什么检索命中率从 16.7% 到 100%？→ 早期基线是"纯向量 + 无阈值过滤"，来源文件匹配几乎全 miss；之后上混合检索（BM25 补字面命中）、调阈值、去重，且评测集本身是"chunk 能回答的问题"，检索命中天然容易达标。100% 那轮是 80 条子集，全量 232 条是 96.1%，更真实。
- Q：LLM-as-Judge 会不会有偏？→ 会。缓解：temperature=0、分数提取归一化、失败给中性分 0.5；更严谨的做法是换一个 judge 模型交叉验证，项目没做，是已知限制。
- Q：四维指标的判定标准是什么？→ 忠实度=论断可被上下文支持的占比；答案相关性=反推问题与原问题 embedding 相似度；精准度=相关 chunk 占比；召回率=标准答案论断被检索到的占比。每个都是 0-1。
- Q：评测集会不会泄漏？→ 评测题是从 chunk 生成的，ground truth 答案必在知识库中，这保证"检索得到就答得出"；但代价是**测不出"知识库外问题"**（out_of_scope 只有 3 条人工造的），泛化性评测偏弱。
- Q：232 条怎么来的 250？→ `--count 250` 生成后：去重相似问题 + 过滤泛泛问法 + LLM 生成失败跳过，实得 232。

### 5. 边界
- **全量批次的四维 LLM 判分缺失**（上面已详述），简历数字与提交 JSON 的字段要对齐口径。
- 评测成本：四维判分每条要 10+ 次 LLM 调用（论断拆解+逐条验证），232 条全量跑非常贵，所以只做了子集。
- `avg_latency_ms` 1.7-1.8s 是**单条串行评测**的耗时（含模型冷启动），不代表线上真实 p95。
- 关键词分公式（0.5/0.2/0.3 权重）是自定义的，不是 RAGAS 标准，解释时要区分"工程指标"和"RAGAS 指标"。
- 评测集是**静态快照**，知识库更新后评测题可能过时（问题对应的 chunk 内容已变），需要重新生成。

## 【设计点5】增量索引（扫描对比 + hash 校验 + 增删改分流）

### 1. 问题
知识库 data/ 目录有 40+ 个文件、3751 个 chunk。每次全量重建：重新解析所有文件 + 全量 embedding + 重写向量库，耗时长、成本高、且会清掉手动调整的元数据。需要"只处理变化的文件"。

### 2. 选型
- **扫描对比 registry（SQLite 存文件 hash）**而不是 inotify 事件驱动作为主机制：启动/定时扫描能自愈（事件丢失也无所谓），实现简单可靠；watchdog 事件监听作为**补充触发**。
- 文件指纹用 **MD5 全文件 hash** 而不是 mtime：mtime 可被 touch 骗过、且不同步；hash 是内容级判断，可靠。代价是每次扫描要全量读文件算 hash（IO 成本）。
- 增删改分流处理：删除走"先删向量再删记录"，修改走"先删旧 chunk 再重新索引"（幂等、无残留），新增走"加载→切片→embed→追加"。
- chunk id 用 `md5(f"{source}_{i}")` 稳定生成：同一文件同一顺序产出相同 id，天然支持 upsert 语义。

### 3. 实现（真实代码）
- **扫描**：`src/core/document_scanner.py`
  - `compute_file_hash`（L33-39）：MD5 分块读（8KB 块）。
  - `scan_data_directory`（L50-94）：按 loader 支持的扩展名 `rglob` 收集磁盘文件（L62-66）→ 读 registry `list_documents()`（L69）→ 逐文件算 hash 对比：磁盘有 registry 无 = `added`；hash 不同 = `modified`；registry 有磁盘无 = `deleted`（L77-92）。
- **执行**：`src/core/incremental_indexer.py`
  - `sync()`（L30-73）：先删（L47-53）→ 再改（L56-62，`_update_file`）→ 后增（L65-71），返回 `{added, updated, deleted, errors}` 统计。
  - `_add_file`（L75-119）：`get_loader_for_file`（插件化 loader）→ `SmartSplitter.split_elements` → `embedder.embed` → `chunk_id = md5(f"{source}_{i}")`（L107）→ `vector_store.add` → `update_registry(file_path, file_hash, len(chunks), "indexed")`（L118）记录 chunk 数和 hash。
  - `_update_file`（L121-130）：**先删旧再重加**（L126-129），保证同文件旧 chunk 不残留。
  - `_delete_file_by_path_str`（L150-161）：`vector_store.get_all()` 全量遍历，按 `metadata["source_file"] == file_path` 匹配收集 id 再 `delete`。
- **事件触发**：`src/core/watcher.py`
  - watchdog `Observer` + `_DebounceHandler`（5 秒防抖，L23/L52-58，防 IDE 连续保存），过滤目录/临时文件（`~`开头、`.tmp/.swp`，L46-50）；
  - `_on_change`（L109-135）：执行 `IncrementalIndexer().sync()` 并通过 WebSocket 广播"索引开始/完成"（data_monitor）。
- **registry 落库**：`src/storage/database.py` 的 `upsert_document` / `delete_document` / `list_documents`（DocumentRecord 含 file_hash、chunk_count、status、indexed_at、error_message）。

### 4. 追问预案
- Q：修改文件为什么要先删整个文件的 chunk 再重建，而不是 diff？→ 切片结果会因内容变化整体漂移（一个段落变了，后面 chunk 边界全变），diff 切片不现实；删了重建最简单且幂等。
- Q：hash 对比和 watchdog 会不会重复触发？→ 会，所以 watchdog 只是触发器，真正判断"要不要索引"在 scan 的 hash 对比里——事件触发的 sync 会再次扫描，没变化的文件 hash 相同直接跳过（不会误索引）。
- Q：删除文件时怎么找到它的 chunk？→ 遍历全部 metadata 匹配 source_file。3751 条全量遍历是 O(N)，可接受；但如果是 100 万级就要在 metadata 上建索引或用 collection 隔离（项目已有 kb_id 分 collection 的能力，`vector_store.py` L207-218）。
- Q：索引一半失败怎么办？→ 每条文件单独 try/except（incremental_indexer L47-71），单文件失败记 errors 不影响其他文件；但**没有事务**，一个文件"删旧成功、加新失败"会残留半更新状态，registry 会记录 error 状态便于人工排查。
- Q：新增 loader 支持新格式？→ `loaders/__init__.py` 的 `LOADERS` 列表注册即可，`get_loader_for_file` 按 `can_handle` 分发，核心代码零改动。

### 5. 边界
- **删除依赖全量遍历**匹配 metadata，chunk 量大时慢；且 `_delete_file_by_path_str` 里 try/except 静默吞异常（L160-161），删失败不报错，registry 可能残留。
- 无事务/无原子性：多文件批量同步中途崩溃，向量库和 registry 可能不一致（下次扫描 hash 对比能部分自愈）。
- 每轮扫描要算所有文件的 MD5，IO 密集；文件多时扫描本身有成本（可接受，因为一般远小于全量重建）。
- `data/` 下还有 `rag.db` 这类非知识库文件，靠 loader 扩展名白名单天然排除（document_scanner L42-47）。

## 【设计点6】会话管理 + 摘要压缩（超长对话）

### 1. 问题
多轮对话有两个矛盾：① 上下文越长，LLM 输入 token 越贵、越容易"失焦"；② 全截断又会丢掉早期关键信息（比如用户第一轮说过的背景）。需要"保留近期 + 压缩远期"。

### 2. 选型
- 会话状态用**进程内 dict**（`sessions: dict[str, Session]`）而不是 SQLite：会话是高频读写、短生命周期，内存存取最快；持久化会话不是需求（用户会话记录另有 query_log 表）。
- **"滑动窗口截断 + LLM 摘要"双机制**：`MAX_HISTORY_ROUNDS=5` 保留最近 5 轮（10 条消息）保证即时上下文；超过 `SUMMARY_THRESHOLD_ROUNDS=5` 时把**全部历史**喂给 LLM 生成一段摘要，存到 session.summary。
- 摘要注入方式：`get_history_with_summary` 把摘要作为 **system message** 放在最前面——因为摘要描述的是"之前的对话"，放 system 位置最符合 LLM 的注意力习惯，且不会被误当成用户最新输入。
- 懒加载 `ConversationSummarizer`：不用就不初始化 LLM client。

### 3. 实现（真实代码）
- 数据结构：`src/core/session.py` L14-30，`Message(role, content, timestamp)`、`Session(session_id, messages, summary, ...)`。
- 存取：`get_or_create_session`（L48-60）自动建会话 + 每 5 分钟触发一次 `cleanup_expired`（超时 30 分钟清理，L51-53、L166-174）。
- 写入与压缩：`add_message`（L62-75）：
  - `USE_CONVERSATION_SUMMARY` 开启时调 `_maybe_summarize`（L77-88）：消息数 > `SUMMARY_THRESHOLD_ROUNDS*2`(10) → `summarizer.summarize(全部消息)` 覆盖写 `session.summary`；
  - 然后无条件截断：`messages[-MAX_HISTORY_ROUNDS*2:]`（L72-75）。
- 摘要实现：`src/core/conversation_summarizer.py` `summarize`（L22-57）：把消息格式化成"用户: ...\n助手: ..."文本，prompt"压缩为简洁摘要，保留关键信息和上下文"，`temperature=0.3, max_tokens=500`；失败降级返回 `[摘要生成失败: ...] 对话包含 N 条消息`（L57），不抛异常。
- 注入：`get_history_with_summary`（L98-117）返回 `[{"role":"system","content":"之前对话的摘要：..."}, ...最近消息]`。
- 实际调用链：`src/api/routes.py` L195-205——`history = get_history(session_id)[:-1]`（去掉刚插入的当前问题），`summary = get_summary(session_id)`，一起传给 `rag_engine.query(question, history=..., summary=...)`；generator.py L69-70 把 summary 拼进 system content（"之前对话的摘要：\n{summary}"）。
- 导出：`export_session_markdown`（L124-164）把会话导出成 md（面试可提：溯源能力延伸到会话级）。

### 4. 追问预案
- Q：摘要和截断的顺序？→ 先判是否触发摘要（>10 条），摘要基于**全部**历史生成；随后窗口截断只留最近 10 条。所以 LLM 看到的 = 摘要(system) + 最近 5 轮。
- Q：摘要会不会重复生成、越滚越差？→ 会重复生成（每次超阈值都对全量历史重新摘要，非增量）；因为原始消息很快被窗口截掉，实际可输入的就是最近 10 条，摘要质量可控但早期细节会丢失——这是"摘要丢失细节"的经典 trade-off。
- Q：为什么不把摘要持久化？→ 会话本就不持久化（内存 dict），重启即失；摘要跟随 Session 对象生命周期。
- Q：history 里包含系统提示怎么办？→ routes.py 里 `get_history` 只返回 user/assistant 消息，system 摘要单独走 summary 参数，两层不混淆。
- Q：并发会话会不会串？→ session_id 是客户端传入的 key，dict 隔离；但**没有锁**，同 session 并发写消息有竞态（低概率，FastAPI 单 worker 下问题不大）。

### 5. 边界
- **会话不落库**：服务重启所有会话丢失（前端 session_id 失效，用户要重新开对话）。这是与"企业级"印象最不符的一点，面试要主动承认并说"下一步可迁移到 Redis/SQLite"。
- 摘要覆盖写而非累积：summary 字段只存最新一版，中间轮次的压缩历史不可追溯。
- 摘要用的是**全部消息**而非"早期消息"（`split_messages` 方法写了但 `_maybe_summarize` 没调用它）——代码里预留了拆分能力但主路径没用，属于"接口与实现不完全一致"。
- `MAX_HISTORY_ROUNDS=5` 截断是**硬截断**，即使没开摘要也生效（L72-75 无条件执行）。

## 【设计点7】链路追踪 + Metrics / Alert

### 1. 问题
RAG 链路有 4 个阶段（查询理解→检索→重排→生成），线上出了问题（慢、报错、幻觉）必须能回答三个问题：这次请求经历了什么？各阶段花了多久？系统整体健康度如何？

### 2. 选型
- 自研轻量 Trace（uuid + span 列表 + SQLite 落库）而不是接 OpenTelemetry/Jaeger：项目是单进程 FastAPI，不需要分布式传播，自研 170 行搞定，零依赖；SQLite 落库便于管理后台查询。
- 指标用**进程内单例收集器**（counter + histogram，含 p50/p95/p99）而不是直接 Prometheus client：先收集再按需 `to_prometheus()` 导出，避免每个请求都格式化文本；导出格式兼容 Prometheus exposition。
- 告警规则简单明确：错误率 >5%（1 分钟窗口）+ 平均延迟 >3000ms（5 分钟窗口），阈值全部 config 化；样本量不足（<10 次）不告警，避免冷启动误报。

### 3. 实现（真实代码）
- **Trace**：`src/core/tracer.py`
  - `Trace(query, user_id)` 生成 `trace_{uuid4().hex[:12]}`（L90）；`start_span(name)` / `end_span(data)` 管理 span（L100-113）；`finish()`（L117-136）把 spans 以 `{stage: {duration_ms, ...}}` JSON 写入 `data/rag.db` 的 `traces` 表（INSERT OR REPLACE，L126-133），带 `_db_lock` 线程锁。
  - 还提供了 `ContextVar current_trace_id`（L21）和 `get_trace`/`list_recent_traces` 查询接口。
- **埋点位置**：`src/core/rag_engine.py` `query()`：
  - `trace = Trace(question, user_id)` + `metrics.inc_counter("total_queries")`（L139-140）；
  - `trace.start_span("query_understanding") / "retrieval" / "rerank" / "generation"`（L195/240/270/321），每个 span 结束带关键数据（子查询数、结果数、token 数）；
  - 直方图：`retrieval_latency_ms`（L262）、`generation_latency_ms`（L341）、`query_latency_ms`（L350）；计数器：`total_tokens_used`（L351）、`total_errors`（L372）。
  - `finally: trace.finish()`（L374-375）保证异常也落库（status 置 "error"）。
- **Metrics**：`src/core/metrics.py`——单例（`__new__` 双重检查锁，L76-83）、`_HistogramBucket` 计算 avg/p50/p95/p99/max（L8-63）、`to_prometheus()` 导出 `rag_total_queries` 等文本（L164-187）、`snapshot()` 含 `error_rate_pct`（L193-206）。
- **Alert**：`src/core/alert_manager.py`
  - `_check_error_rate`（L37-66）：60 秒窗口检查一次，`total < 10` 不告警，错误率 >5% 触发 `high_error_rate` 并 `record_alert`；
  - `_check_latency`（L72-95）：300 秒窗口，`count < 5` 不告警，`avg > 3000ms` 触发 `high_latency`；
  - 告警历史保留最近 1000 条（metrics.py L136-138），管理后台可查。
- **API 出口**：routes.py 提供 /traces、/metrics、/alerts 类接口（前端 Dashboard/IndexMonitor 消费）。

### 4. 追问预案
- Q：trace 为什么不用 OpenTelemetry？→ 单进程单体足够；OTel 的收益在分布式/多服务，这里引入是过度设计。如果未来拆服务，Trace 的 ContextVar 结构可以平移到 OTel span context。
- Q：p95 怎么算的？→ 对窗口内所有值排序取 95% 分位（metrics.py L35-41），是近似分位数（非直方图分桶），样本少时粗但够用。
- Q：告警只有日志没有通知？→ 对，当前告警落到 metrics 内存 + logger.warning，没有接钉钉/邮件/webhook；接口已留（record_alert），接通知是下一步。
- Q：异常请求 trace 能看到吗？→ 能，异常时 `trace.status="error"` 且 finally 落库，stages 里能看出卡在哪个阶段（比如 generation 缺失说明检索/重排阶段挂了）。
- Q：metrics 重启会丢吗？→ 会，纯内存；SQLite 只存了 trace 明细，指标聚合没持久化。

### 5. 边界
- 单进程假设：多 worker/多实例部署时 metrics 各自为政，Prometheus 抓取会重复计数（需按实例 label 区分，当前没做）。
- 告警阈值是硬编码经验值（5%/3000ms），没有自适应基线。
- `maybe_reset_window` 只清直方图不清计数器（计数器是全生命周期累计），所以 `total_queries` 是累计值、错误率按累计算，窗口重置对错误率告警影响有限——这是个隐藏小坑。
- trace 表无清理机制，长期运行会无限增长（每次查询一条记录）。

## 【设计点8】LangChain 双引擎（自研 vs LangChain，LCEL 管道）

### 1. 问题
项目先自研了完整 RAG 链路（rag_engine.py），后来要"对齐业界主流框架"（简历话术、可维护性、生态），引入了 LangChain 重构。需要两套引擎**可切换、接口兼容**，且切换不破坏 API 层、评测层、前端。

### 2. 选型
- 用**环境变量 `RAG_ENGINE=langchain|original` 编译期选择**而不是运行时策略模式：两引擎都较重（模型加载、索引构建），启动时二选一加载，避免双份内存（尤其 embedding 模型）。
- LangChain 版用**LCEL（Runnable 管道）**声明式组装：`context: retriever | format_docs`、`question: RunnablePassthrough()` → `prompt` → `llm` → `StrOutputParser()`，可读、可测试、可单独替换节点。
- 混合检索用 LangChain 官方 **`EnsembleRetriever`**（vector 权重 0.6 + BM25 0.4）对齐自研版的 RRF 思路。
- 保留自研版：自研版功能更全（意图识别/缓存/摘要/HyDE），LangChain 版作为"标准实现"和性能对照组。

### 3. 实现（真实代码）
- **切换点**：`src/config.py` L39 `RAG_ENGINE = os.getenv("RAG_ENGINE", "langchain")`（**默认 langchain**）；`src/api/routes.py` L38-46 模块导入时 `if RAG_ENGINE == "langchain": from src.core.langchain_rag import LangChainRAGEngine ... else: from src.core.rag_engine import RAGEngine ...`，两个引擎都暴露 `query()` / `query_stream()` 兼容接口。
- **LCEL 管道**：`src/core/langchain_rag.py` L156-161：
  ```python
  self.chain = (
      {"context": retriever | format_docs, "question": RunnablePassthrough()}
      | self.prompt | self.llm | StrOutputParser()
  )
  ```
  prompt 是 `ChatPromptTemplate`（L130-142），要求回答末尾标 `[来源X]`。
- **EnsembleRetriever**：L103-125 `_setup_hybrid_retriever`——`BM25Retriever.from_texts(texts, k=top_k)`（L110-113）+ `EnsembleRetriever(retrievers=[vector_retriever, bm25_retriever], weights=[0.6, 0.4])`（L115-118）；失败降级 `use_hybrid=False` 纯向量。
- **query() 实际流程**（L166-297）：多子查询（可选）→ `vectorstore.similarity_search_with_score(q, k=top_k*2)` 每路取 2 倍候选（L208）→ `score = 1.0 - dist` → 内容 hash 去重（L212-215）→ 按分排序 → `score < relevance_threshold` 过滤（L227，.env 里 0.55）→ 可选 Reranker 精排（L242-259）→ 用与 sources 一致的 context **绕过 chain 内部重复检索**、直接 `prompt|llm|StrOutputParser` 生成（L271-275）。
- **查询扩展兼容**：L194-201 复用自研 `QueryUnderstander().expand_query()`，扩展失败静默忽略。
- **添加文档**：`add_documents`（L357-392）用 `RecursiveCharacterTextSplitter(chunk_size=800, chunk_overlap=100, separators=["\n\n","\n","。","！","？","，"," "])`（L365-370）切分后 `add_texts`，随后重建 BM25 + 重建 chain。
- **评测复用**：`evaluate.py` L259-269 复用引擎内 embedding 避免 bge-m3 被加载两次（Windows 下会段错误），这是踩坑后的修复。

### 4. 追问预案
- Q：两套引擎结果一样吗？→ 不一样。差异点：① 混合检索权重（自研 RRF k=60 等权 vs LangChain 0.6/0.4）；② LangChain query() 主路径实际没走 ensemble（用 similarity_search_with_score）；③ 自研版有意图/缓存/摘要，LangChain 版 history 参数是"预留未用"。切换引擎会改变线上行为，评测时要固定引擎。
- Q：为什么默认用 LangChain 版？→ 对齐业界主流（README/简历口径），且 LCEL 管道对后续接 LangSmith、换 retriever 更友好；代价是部分自研能力（意图/缓存）在 LangChain 版没实现。
- Q：LCEL 比手写好在哪？→ 声明式、节点可替换（换 retriever 只改一行）、天然支持 stream/async/batch，`.stream()` 直接出打字机效果（query_stream L339）。
- Q：为什么 generation 阶段绕过 chain？→ 因为 query() 已经手动做了检索+过滤+rerank，如果调 self.chain 会再检索一次（浪费且结果不一致），所以现场拼 `{"context": lambda _: context, ...}` 复用已处理的 sources。
- Q：两引擎怎么保证接口一致？→ 都返回带 answer/sources/usage/timing 的对象（RAGResponse vs LangChainRAGResponse 字段对齐），routes.py 里统一取 `response.answer/sources`。

### 5. 边界
- **LangChain 版 query() 主路径不是真混合检索**（前面已述），只有 query_stream 走 ensemble——这是代码里最容易被面试官抓到的"名不副实"点，主动讲反而加分。
- `BM25Retriever.from_texts` **没传 tokenizer**，LangChain 默认分词对中文效果差（不像自研版显式 jieba）——中文场景下 LangChain 版 BM25 通道是"有但弱"。
- `usage` 恒为 `{}`：LangChain 不直接暴露 token 用量，成本统计在 LangChain 版缺失。
- 引擎在 routes.py 模块级单例初始化：**改 RAG_ENGINE 必须重启服务**；且模型加载失败会导致整个 API 起不来（没有运行时降级到另一引擎）。
- import 用了 `langchain_classic` 这个第三方包名（L10），依赖较冷门，部署时需注意锁定版本。

## 【设计点9】文档解析与切片（MarkdownSplitter / 递归兜底 / 表格图片保护）

### 1. 问题
知识库文档格式杂（md/txt/docx/pdf/图片/表格），chunk 质量直接决定检索上限。三个核心诉求：① 按语义结构（标题）切而不是无脑按字数；② 表格/代码块/图片这类**整体才有意义**的内容不能被切断；③ 长 section 要有兜底切分 + 重叠，避免上下文断裂。

### 2. 选型
- **Loader 插件化**：每种格式一个 loader（`loaders/__init__.py` 的 LOADERS 列表），统一输出 `DocumentElement(content, element_type, metadata)`——解析与切片解耦，新格式只加 loader。
- **按标题层级切分**（MarkdownSplitter）优先：标题是文档的天然语义边界，切出的 chunk 自带 `section` 元数据（回答引用"文件名+章节名"就靠它）。
- **短 section 向后合并**：孤立标题（<100 字）合并到下一节，避免无效 chunk 浪费 embedding 额度。
- **长 section 按字数兜底**：800 字符 + 100 重叠（config 默认；.env 实际覆盖为 500/50）。
- **表格/图片/代码块整体保留**：这些元素切开就废了；表格另可配 `TABLE_NL_DESCRIPTION` 生成自然语言描述（默认关，因为要多一次 LLM 调用）。
- 通用文本用**递归字符切分**（先按段落、再按句子、最后按字符）兜底，对齐 LangChain RecursiveCharacterTextSplitter 的思路。

### 3. 实现（真实代码）
- **Loader 层**：`src/core/loaders/`——`base.py` 定义 `ElementType(TEXT/TABLE/IMAGE/LIST/CODE/IMAGE_DESCRIPTION)` 和 `DocumentElement`；markdown/docx/pdf/txt/image 各一个 loader；`__init__.py` 的 `get_loader_for_file` 按 `can_handle` 分发。
- **SmartSplitter**：`src/core/splitter.py` L17-105
  - `split_element`（L61-105）：TABLE/IMAGE_DESCRIPTION/CODE 直接整体成 1 个 chunk（L71-88）；文本走 MarkdownSplitter，`len(chunks)==1 且内容 < chunk_size/2` 时改用 RecursiveCharacterSplitter 兜底（L102-103，判断"这不是 markdown"）。
  - 表格增强：L49-54，`TABLE_NL_DESCRIPTION` 开启时 `enrich_table_element`（preprocessor.py 的 `table_to_markdown` + LLM 描述）生成后按元素再切。
- **MarkdownSplitter**：L108-219
  - `_split_by_headers`（L161-203）：按 `^(#{1,3})\s+` 标题切；**```` ``` ```` 代码块状态机保护**（L174-181，代码块内标题不切）；当前 section 记录 `header` 字符串。
  - 短合并：L125-131，`len(content) < 100` 且后面还有 section 时拼到下一个。
  - `_split_by_size`（L205-219）：`start = end - chunk_overlap` 滑窗切分（800/100）。
- **RecursiveCharacterSplitter**：L222-292，分隔符优先级 `["\n\n", "\n", "。", "！", "？", ".", "!", "?", " "]`，递归切分（L248-281），没有可用分隔符时按字数硬切。
- **参数**：`src/config.py` L42-43 `CHUNK_SIZE=800`、`CHUNK_OVERLAP=100`（.env 覆盖为 **500/50**——以 .env 为准）；`build_index.py` 用 `SmartSplitter()` 并行（ThreadPoolExecutor）处理全量文件。
- 元数据贯通：每个 chunk 带 `source_file / section / chunk_index / content_type / page_number`，检索结果引用溯源（前端展开原文）和 RAGAS 的 retrieval_hit 都依赖这些字段。

### 4. 追问预案
- Q：为什么表格不切？→ 表格一行没意义、整表才有信息量（且 RAG 检索表格通常整表命中）；切开后 embedding 和生成都会"断章取义"。
- Q：重叠 100 字符会不会重复计算 token？→ 会，重叠 chunk 内容有重复，embedding 存储和 LLM 上下文都有冗余，但换来的是"边界信息不丢失"，检索质量收益大于成本。
- Q：代码块不切有什么代价？→ 超长代码块会整块超过 chunk_size（800），embedding 上限/检索时可能截断——项目选择"完整性优先"，代价是超长代码块检索效果差。
- Q：为什么 .env 里是 500/50？→ 调参后的结果（chunk 更小、检索更聚焦），README 的 800/100 是 config 默认值；面试讲参数时说明"默认 800/100，当前环境 500/50"，体现你了解配置驱动。
- Q：PDF 怎么解析？→ pdf_loader（pdfplumber），表格/图片元素由 loader 标注类型，走同一套 SmartSplitter。
- Q：section 元数据是嵌套层级吗？→ 不是，只记录**最近一个标题字符串**（`current_header` 会被新标题覆盖），丢失了多级标题的层级结构——这是简化，可接受因为引用只需要"章节名"。

### 5. 边界
- 标题切分只支持 `#`/`##`/`###`（正则 `#{1,3}`），四级标题 `####` 不会触发切分。
- 中文按字符 `len()` 切分：英文场景单词可能被从中间截断（无 tokenizer 感知），中文场景影响小。
- `chunk_index` 在 MarkdownSplitter 超长分支里是子块序号（L146）、在短分支里是全局累计（L154），语义不一致，只是展示用。
- 表格 NL 描述默认关闭（多一次 LLM 调用 + 成本），图片 OCR/描述也靠 `MULTIMODAL_ENABLED`/`IMAGE_LLM_DESCRIPTION` 开关（.env 里开了 MULTIMODAL_ENABLED=true 但 TABLE_NL_DESCRIPTION 未显式开）。

## 【设计点10】Embedding 与 ReRanker（bge-m3 本地部署 + bge-reranker-base 精排 + HNSW）

### 1. 问题
① 中文 embedding 质量决定检索上限——通用英文模型（all-MiniLM-L6-v2）对中文效果差；② 召回的候选集可能有噪声，需要第二级"精排"；③ 向量库的索引参数（空间度量/近邻搜索）影响召回质量与性能。

### 2. 选型
- Embedding 选 **bge-m3**（BAAI，多语言/中文强，1024 维，支持 dense+sparse+colbert 三种表示）并**本地部署**（models/BAAI/bge-m3 目录有完整权重 + onnx）：不依赖外部 API，免费用、无延迟波动、数据不出内网（企业诉求）。用 `EMBEDDING_PROVIDER=local` 开关，预留 deepseek api 通道。
- ReRanker 选 **bge-reranker-base**（CrossEncoder）：CrossEncoder 把 query 和 doc 拼一起过 Transformer，比 BiEncoder（双塔）精度高一个档次，适合做第二级精排；base 版体积/速度均衡（评测指南里提到权重 1.1GB）。
- 向量库用 **ChromaDB + HNSW**：HNSW 是近似近邻搜索（ANN）的主流图索引，召回率/延迟均衡；Chroma 默认持久化到本地目录（chroma_db/）。
- 两阶段"召回→精排"是 RAG 标准范式：第一阶段用便宜的双塔（向量/BM25）召回 top_k，第二阶段用贵的 CrossEncoder 精排——把 CrossEncoder 用在全部 3751 条上不现实。

### 3. 实现（真实代码）
- **Embedder**：`src/core/embedder.py`——`SentenceTransformer(EMBEDDING_MODEL)` 懒加载（L17-23），`embed`/`embed_single` 批量/单条编码；config `EMBEDDING_MODEL = "models/BAAI/bge-m3"`（**相对路径**，指向仓库内本地权重，已核对目录含 pytorch_model.bin/sentencepiece.bpe.model/onnx/ 等）；`EMBEDDING_PROVIDER=local`（.env 显式）。
- **Chroma 后端**：`src/core/vector_store.py` `ChromaBackend`（L73-148）
  - `PersistentClient(path=CHROMA_DB_DIR)`（L83-86）；
  - collection 创建时 `metadata={"hnsw:space": "cosine"}`（L94-97）——**只显式设置了距离度量 cosine，M/efConstruction 等 HNSW 参数用 Chroma 默认值**；
  - 门面 `VectorStore` 支持按 kb_id 分 collection（L207-218）、跨库并行检索（L315-365，ThreadPoolExecutor ≤4 worker，按 cosine 距离升序合并）。
- **Reranker**：`src/core/reranker.py`——`CrossEncoder(RERANKER_MODEL)` 懒加载（L24-28），`rerank(query, documents, top_k)` 构造 `(query, doc["content"])` 对 → `model.predict(pairs)` → 按分数降序取 top（L30-60）。
- **接入点**：`rag_engine.py` L269-287——rerank 前把 RRF 合并去重后的结果转成 `{content, metadata}`，`reranker.rerank(question, docs, top_k)`，rerank 后**分数被 CrossEncoder 分数覆盖**（原 RRF 分数只用于排序阶段）；`use_reranker` 构造参数默认 true（rag_engine `__init__` L42），config `USE_RERANKER` 默认 false（.env 未开）。
- **LangChain 版**：`langchain_rag.py` L73-77 `HuggingFaceEmbeddings(model_name=EMBEDDING_MODEL, device="cpu", normalize_embeddings=True)`——注意这里**做了归一化**，而自研 Embedder 没归一化（encode 默认不归一化），两引擎 embedding 行为不一致；reranker 复用自研 `Reranker`（L244-259）。
- **维度/存储**：bge-m3 1024 维，chunk 数实测 3751（chroma.sqlite3 核对）。

### 4. 追问预案
- Q：bge-m3 和 all-MiniLM 差在哪？→ 语言覆盖（中文强）、维度（1024 vs 384）、检索方式（bge-m3 支持 dense/sparse/colbert 多路，本项目只用 dense 部分）。
- Q：为什么 reranker 用 CrossEncoder 不用更大的模型？→ base 版精度/速度均衡；rerank 只对 top_k（≤20）条打分，CrossEncoder 的 O(N) 逐对计算可接受；更大模型边际收益低、延迟高。
- Q：HNSW 参数为什么没调？→ 3751 条规模下 HNSW 默认参数（M=16、efConstruction=200、efSearch 默认）足够，参数调优收益出现在百万级；如果数据量上来，再显式传 `hnsw:M`、`hnsw:ef_construction`、`hnsw:search_ef`。
- Q：cosine 距离怎么转分数？→ 自研版 `score = 1 - distance/2`（retriever.py L41，cosine 距离 ∈[0,2]）；LangChain 版 `1.0 - dist`——**两套换算不一致**，阈值 0.55 只在 LangChain 版语义下成立。
- Q：embedding 模型加载失败会怎样？→ Embedder 里 `SentenceTransformer` import 失败会 raise ImportError（L20-21），懒加载直到第一次检索才炸——没有优雅降级到 API embedding（config 预留了 EMBEDDING_PROVIDER=api 但代码里 embedder.py 没有实现 API 分支！）。诚实说：**API embedding 通道是 config 预留，实际只实现了 local**。

### 5. 边界
- **embedder.py 只实现了本地模型**：`EMBEDDING_PROVIDER=api` 的开关在 config 里，但代码没有 API 分支，改配置会直接 ImportError/加载失败——"可切换"是半成品，面试别吹 API 切换。
- 自研版与 LangChain 版 embedding 归一化不一致（影响分数含义与阈值）。
- reranker 分数与检索分数**不可直接比较**（不同模型输出域），代码里 rerank 后直接用其分数做排序和展示，阈值过滤在 rerank 之前已用检索分数做过。
- bge-reranker-base 首次加载要下权重（约 1.1GB，评测指南第4轮记录），离线环境需预置模型；CPU 上 rerank 20 条约几百 ms 到秒级，是全链路延迟大头之一。
- Chroma 的 HNSW 参数未显式调优、无分片（单 collection 3751 条没问题，百万级要切 Milvus——config 的 `VECTOR_STORE_BACKEND` 同样只是预留，工厂只实现了 chroma，见 vector_store.py L164-172）。

## 给面试官的一句话总结

1. **混合检索+RRF**：向量和 BM25 双通道各自 top_k 召回，用加权 RRF（w/(k+rank)）按排名融合，BM25 索引构建失败自动降级纯向量，服务不挂。
2. **查询理解三阶段**：LLM 先纠错（同音字）、再拆 3-5 个子查询多路召回 + md5 去重、HyDE 生成假设文档补语义鸿沟，每步失败都静默降级为原 query，全部开关化。
3. **意图识别+LRU 缓存**：关键词 O(1) 快判闲聊/反馈，判不了再花 20 token 让 LLM 分类，四类意图分流路由；检索结果用 cachetools TTLCache（1000 条/1h）按 md5(query||top_k) 缓存，命中省检索不省生成。
4. **RAGAS 评测**：3751 个 chunk 分层抽样 + LLM 自动生成 232 条带标准答案的评测集，四维 LLM-as-Judge 指标（忠实度/答案相关性/上下文精准度/召回率）定位瓶颈，控制变量调优把检索命中率从 16.7% 提到 100%（全量 232 条 96.1%）、RAGAS 总分 0.59→0.65。
5. **增量索引**：扫描 data/ 目录算 MD5 对比 SQLite registry，hash 变了才重索引，新增/修改/删除分流处理，watchdog 5 秒防抖触发 + WebSocket 广播进度。
6. **会话+摘要压缩**：SessionManager 内存 dict 存会话（30 分钟超时清理），超 5 轮把全部历史 LLM 压成摘要放 system message，再加最近 5 轮滑动窗口。
7. **链路追踪**：每次问答生成 trace_id，查询理解→检索→重排→生成四阶段 span 落 SQLite，Metrics 单例收集 counter/直方图（p50/p95/p99）并导出 Prometheus，错误率 >5% 或延迟 >3s 自动告警。
8. **LangChain 双引擎**：RAG_ENGINE 环境变量二选一，LangChain 版用 LCEL 管道（retriever|format_docs → prompt → llm → StrOutputParser）+ EnsembleRetriever（0.6/0.4），自研版功能更全，两套 query/query_stream 接口兼容。
9. **切片**：按 Markdown 标题（#~###）切分 + 代码块状态机保护 + 短 section 向后合并，表格/图片/代码整块保留，超长按 800 字+100 重叠兜底，非 Markdown 走递归字符切分（段落→句子→字符）。
10. **Embedding+ReRanker**：bge-m3 本地部署（1024 维，models/ 下完整权重）做召回，bge-reranker-base CrossEncoder 对候选精排，ChromaDB 用 cosine 空间的 HNSW 索引持久化。
